# PocketPlanner architecture

## Ownership

- `planner_store.py` owns the versioned workspace contract, validation, SQLite state, revision checks, and explicit replacements.
- `pockethive_auth.py` owns the outbound PocketHive authentication adapter and the local-admin editing policy. PocketHive remains the identity owner.
- `server.py` owns the single Starlette/Uvicorn HTTP process, static delivery, response security headers, and the mounted MCP transport lifespan.
- `planner_live.py` owns bounded SSE subscriptions and one committed-revision observer, reading through `planner_store.read_revision`; it never saves state or resolves editing permission.
- `planner_commands.py` owns scoped read/create/patch command composition. It calls the existing store owner for all data validation, atomic persistence, and revision checks; it never resolves identity or edits SQLite directly.
- `planner_issues.py` composes activity assignment changes against a validated plan, narrowing broad issue scopes without changing other activities' assignments. Validation and persistence remain in the store.
- `planner_execution.py` composes factual Started/Done transitions and blocker intervals during the store transaction; it has no database, identity or HTTP access.
- `planner_mcp.py` owns SDK tool registration, request-scoped PocketHive access checks, tool-error projection, and MCP Host/Origin allowlists. It does not implement the MCP wire protocol or store state.
- `planner_version.py` loads and validates the single application-version source in `VERSION`; HTTP, MCP and UI consume this metadata rather than maintaining their own versions.
- `web/auth.js` consumes the existing PocketHive browser session contract and the server's access projection. It does not grant editing rights.
- `web/app.js` owns interaction and read-only projections of the active plan. The named empty-plan view is a presentation for an empty workspace, not persisted domain data.
- `web/progress.js` owns the shared overall-progress projection: rounded equal-weight mean of activity percentages, or no value for an empty collection.
- `web/schedule.js` owns UTC calendar arithmetic, scheduled-day projections, blocker forecasts, continuous task frames, clipping and progress placement. Activity end dates, overdue checks, collapsed summaries, editor previews and drag snapping all use this owner.
- `web/live.js` owns revision invalidation delivery, canonical snapshot loading and reconnect/defer handling; `web/app.js` supplies interaction locks and applies the snapshot without rebasing a draft.
- `web/whatif.js` owns ephemeral preview assumptions and controls. It selects issue targets through the existing scope predicate and calls the calendar owner for projections, never persistence.
- `web/brand.css` owns PocketHive Press Set presentation tokens; `seed.json` owns the empty initial workspace.
- `import_workspace.py` dispatches an explicit operator-requested replacement to the store owner.

## Data contract

`GET /api/state` returns `{schemaVersion: 1, revision, plans}`. Each plan has required `id`, `name`, `description`, `streams`, `activityTypes`, `activities`, and `issues`. The description holds up to 12,000 characters. Streams have `id`, `name`, and `description`, with optional `dependsOn` (an existing predecessor stream ID or null). There are no parallel/sequential flags or fixed resource limits.

Plans accept optional `deadline`, an exact ISO calendar date or null. Absence/null means no target; reads do not rewrite existing plans. It is independent of the calculated finish, unchanged by Activity edits and hypothetical schedules. UI Plan details and scoped MCP create/update commands use the same validation and revision owner. Clearing saves null.

An activity has required `id`, `name`, `streamId`, `typeId`, `start`, `durationDays`, `progress`, `status`, `issueIds`, and `jiraUrl`, plus optional boolean `includeWeekends`. False or omission means Monday–Friday; true includes all calendar days. Duration is the full estimate of scheduled days, 1–365, never remaining time. The inclusive planned end is the last scheduled day. Weekend starts without opt-in begin on Monday, retaining the authored date. No public holidays are inferred. Progress is an integer 0–100. Jira URLs are empty or HTTPS links; no Jira API is called.

Activities also accept optional `dependsOn` (an existing activity ID within the same stream or null). The calendar owner resolves finish-to-start dependencies: a successor starts on the next eligible day after its predecessor's full planned work, not its remaining work. Stream successors follow the last scheduled day of all predecessor-stream activities. Independent roots in a dependent stream shift as a group, preserving their normalized calendar-start offsets, with each root snapping forward over weekends if required; internal activity dependencies then resolve normally. Self references, cycles, cross-stream activity dependencies, missing targets and empty predecessor streams are rejected. Missing/null dependencies preserve manual scheduling. Authored starts are retained as fallback dates; effective schedules are derived projections, not persisted rewrites. Progress does not affect the authored estimate schedule; interrupted-work forecasts use approximate remaining effort.

Activity types have `id`, `name`, and a hexadecimal color. Issues have `id`, `title`, `description`, `scope`, `streamIds`, `blocker`, `discovered`, `open`, `descriptionIncomplete`, and `jiraUrl`, with optional `activityIds`. Scope is explicitly `ALL` with empty target lists, `STREAMS` with at least one existing stream ID and no activity targets, or `ACTIVITIES` with an explicit list of existing activity IDs and no stream targets. An empty ACTIVITIES list means no affected activities. An open blocker affects its scope; this remains the single authority for blocking and list counts. Activity `issueIds` are retained links and, when explicitly edited through a scoped activity command, specify the desired actual assignments. The command updates affected issues atomically: unlinking one activity from ALL/STREAMS narrows the issue to ACTIVITIES for the remaining currently affected activities. Other assignments, lifecycle flags and timestamps are preserved. Newly created activities follow ALL/STREAMS scopes unless explicitly excluded; narrowed ACTIVITIES scopes target only their explicit IDs. The activity editor shows actual scope membership, never stale context links. A raw workspace replacement uses its explicit issue scopes without inferring assignment changes from issueIds. References resolve within their plan; duplicate IDs within one collection fail.

Issues can also have `resolvedAt`, a timezone-aware ISO timestamp or null. Absence/null means the resolution time was not recorded, not that the issue is still open. The store stamps UTC time on a saved open-to-closed transition, preserves a recorded time while the issue remains closed, and clears it on reopening. Timestamps are scoped by plan and issue ID. Newly imported closed issues retain supplied valid historical timestamps; missing dates remain unknown. Explicit offline replacement imports historical state rather than inventing lifecycle events. No read-time migration or guessed dates are used.

`PUT /api/state` requires a verified editor and the full versioned workspace. Matching revisions save atomically and increment the revision; stale revisions return 409. Invalid input returns 400. Anonymous writes return 401, non-editor writes return 403, and an unavailable auth owner denies authenticated writes with 503. Mutation success is the canonical saved document returned by the store.

`PUT /api/activities` uses the same permissions, size limit, store and revision guarantees for the activity editor. Its body is `{planId, activityId, item, expectedRevision}`; activityId is null for explicit creation or the unchanged existing item ID for an update. It composes the activity edit and requested issue assignments through `planner_commands` and returns the full canonical workspace. No implicit upsert is allowed. Other editor/drag/import operations retain the workspace endpoint. Deleting a predecessor with remaining dependants is rejected; deleting an activity removes its explicit ACTIVITIES issue targets in the same save.

On a browser revision conflict, the editor closes before the latest workspace is loaded. Its unsaved draft is discarded with an explicit notice; users must reopen details and review/reapply the intended change. Closed editor forms cannot submit or delete. The browser never reuses stale form values with a refreshed revision, including when the edited item or plan was removed by another session. Drag conflicts reload canonical state without replaying the move.

The browser permits one pending mutation at a time. While its response and any conflict reload are pending, editor fields/buttons are disabled, Save displays Saving…, Escape/Cancel/Close cannot dismiss the editor, and opening another editor, resubmitting, deleting, dragging or importing is blocked. The outgoing form data is captured before controls are disabled. A finally block restores the exact prior disabled states on success, HTTP errors, malformed responses and network errors. Other browser sessions and MCP remain independent; server revision/auth checks still enforce concurrent writes. No request cancellation or draft replay is implied by this interaction lock.

Editor and sign-in dialogs also close when a primary pointer press and click both occur outside their border bounds. Interior/border clicks and text-selection drags starting inside do not dismiss them or activate background controls. Editor dismissal discards the draft like Cancel and remains disabled while a mutation/conflict reload is pending. The full-block warning deliberately keeps its explicit Acknowledged/Show me the blockers requirement; neither backdrop nor Escape bypasses it.

JSON import uses the same versioned contract and mutation endpoint. It replaces all plans only after explicit confirmation. The UI sets the imported revision to the current workspace revision; it does not accept obsolete schemas or migrate formats implicitly. Operational import files are outside the public source and image.

Browser exports use compact UTF-8 JSON, without indentation, and reset only the exported revision to zero. This keeps valid exports within the existing one-MiB file/request limit rather than inflating them with whitespace. Import still applies canonical validation and final saved-size checks; it does not bypass revision growth or server-owned metadata limits.

Export filenames use the selected plan's trimmed name with filename-invalid characters replaced by hyphens, trailing dots/spaces removed and reserved Windows device names prefixed with an underscore. Empty/sanitized-empty names use the explicit generic filename `pocketplanner-plan.json`. Selection changes naming only: the content remains the full workspace, with all plans and no saved-state mutation.

Calendar dates must be exactly ASCII `YYYY-MM-DD` and valid calendar dates; compact and ISO-week forms are rejected rather than normalized. Every persisted ID is literal and must have no leading/trailing whitespace. Referenced IDs are compared literally; there is no trimming during persistence or lookup.

The store owns a shared one-MiB document limit measured as compact UTF-8 JSON bytes, not character count. It validates incoming documents and checks the final serialized state after server-owned timestamps and revision increments, before SQLite commit. HTTP, MCP, and explicit offline replacement share this boundary. Oversized edits leave saved state and revision unchanged. Transport request limits use that same constant; a small scoped MCP command cannot grow the saved workspace past the full-document limit.

## Activity execution timing

Optional `startedAt` and `completedAt` are timezone-aware ISO timestamps recorded by the server on scoped Started/Done actions (including MCP). Actions `started`/`done` are boolean inputs, never saved fields. Done requires 100%; a saved progress transition to 100 also records completion. A progress decrease clears completion, retaining the start. Recorded facts cannot be patched; valid historical timestamps can be supplied for new explicitly imported records. Missing timestamps mean Not recorded, never percentages or planned/discovery dates.

Optional `blockerTrackingSince` and `blockerIntervals` record blocking observed during saves after a recorded start. Each span has historical `issueId`, `title`, `startedAt`, `endedAt` (null while active). The shared issue-scope predicate opens/closes spans when blocking begins/ends, scope changes, assignments are removed, issues are deleted or the Activity completes. History remains after issue deletion and does not imply a live assignment. Maximum 1000 spans per Activity, with validated chronology. No retroactive inference from discovery dates. Every transport uses this composition inside the revision-checked store transaction; recorded fields are not MCP-editable.

Actual duration is elapsed calendar time from Started to Done, or now for unfinished work. Missing facts produce Not recorded. Recorded blocking is the clipped union of spans, counting overlapping blockers once; it is already included in elapsed time and never added again. Labels state tracking coverage. Full working/calendar-day estimates, approximate remaining scheduled days and actual elapsed time are distinct.

Activity details additionally show Blocker delay: the positive calendar-day finish difference between the blocker-aware forecast and the same forecast with blocking interruptions removed, retaining progress and dependencies. The calendar owner returns this per-Activity projection, including inherited predecessor delays and without adding overlapping issues independently. It is estimated finish slip, not the elapsed duration of a blockage or a substitute for missing recorded facts; it is never added to actual elapsed time. Duration has adjacent −/+ buttons around its single numeric input. Buttons step one full planned day, preserve the 1–365 integer limits and invalid drafts, update the preview immediately and never save without Save. Viewer and pending-save locks also cover these buttons.

## Normal blocker-aware forecast

In a continuous frame, paused days take precedence over weekend-only gaps. A paused excluded weekend carries both pause classification and a weekend marker: the red pause color takes precedence over grey weekend coloring for Activities and collapsed Streams, without changing scheduled effort or progress. Extending a blocker from Friday through Saturday/Sunday visibly extends that pause even if work still resumes Monday.

A recorded Started anchors remaining work to the actual start/reference day rather than a later authored start. Actual Activity/Stream predecessor constraints still apply; unchanged full estimates remain available separately. Stream frames aggregate each member's available work after its own pauses: a day is paused only when no member can work and at least one member is paused within its frame. Independent work, opted-in weekends and recorded completed ranges therefore remain visible despite another member's blocker; summary progress uses available scheduled days.

Recorded completion does not switch summary progress to the elapsed calendar span. The calendar owner counts the union of available scheduled and actual-range days, excluding each member's own pauses, non-working weekends and idle gaps. Overlapping members count once and opted-in weekends count as work. Range arithmetic keeps long actual histories bounded rather than allocating one entry per elapsed day; clipping preserves the full-frame progress position.

`PocketSchedule.forecast` derives the normal timeline from authored starts/full estimates, issue scopes and blocking history. Every affected open blocker lasts through the supplied reference calendar day inclusive; predicted resumption is no earlier than the following day, snapping over excluded weekends. Recorded resolution/start/completion timestamps map to the viewer's local calendar, consistently with today's line and actual-time labels; calendar-string arithmetic remains UTC to avoid daylight-saving day-length errors. Known ended Activity blocking intervals are retained even after unlinking/deletion. No missing resolution date is guessed. Overlapping intervals are combined as calendar constraints, never added as independent delay totals. Existing dependency and approximate remaining-effort rules are shared with What if. Completed tasks with a recorded completion use that actual end and the known actual start; without completion facts they retain the estimate frame. Known completed pause annotations do not move completion. Long actual frames are evaluated only within the visible calendar window, not expanded into unbounded day arrays.

The forecast is not persisted. Authored estimates remain the reference for overdue checks and estimate details. Editors preview the same derived dependency/blocker dates; actual elapsed/blocked time still uses server timestamps and interval unions, not these whole-day assumptions. Normal and What if forecasts call the same engine: an optional `{issueId, endDate}` changes only one open blocker's inclusive end, without adding already-counted delays again. A calendar-day rollover refreshes the derived schedule when drafts, saves and drags are unlocked, recalculating a valid assumption or explicitly rejecting a date now in the past. It never rebases a draft. Persisted revisions remain unchanged.

## Authentication

`POCKETHIVE_AUTH_BASE_URL` explicitly selects the PocketHive auth service through its public ingress, including `/auth-service`. No protocol/provider fallback is used. Every authenticated mutation resolves the bearer token at `GET /api/auth/me`; active username `local-admin` is the editor policy. PocketPlanner has no user or password database and does not decode or trust unverified token claims.

Authentication requests never follow HTTP redirects, including same-origin redirects. An unexpected redirect fails closed with 503 before sending a bearer token or login body to a redirect target. Configure the canonical auth ingress directly, including the intended HTTP/HTTPS scheme and path.

`GET /api/session` returns the access projection. `POST /api/session/login` delegates `{username}` to the existing PocketHive `POST /api/auth/dev/login` flow. The browser uses the canonical `PH_UI_V2_AUTH_SESSION` session-storage key and attaches its bearer token. UI controls mirror permissions; the server enforces them independently. Tokens are not persisted in SQLite or source.

Read-only access is the default, including when auth is not configured. The PocketHive DEV login is intended for the same trusted development environment as PocketHive; production identity changes must be implemented at its owner and adapted explicitly here.

## Application version

`VERSION` contains the running application version, including an explicit `-dev` suffix for pending work. `planner_version.py` fails startup for a missing/invalid value. Public `GET /api/info` returns `{name, version}` without reading or changing the workspace. MCP initialization reports the same version. The browser displays this metadata as a muted top-bar label; a metadata-fetch error shows Version unavailable rather than an invented version, without preventing access to the plan. Image publication uses VERSION for its OCI version label and rejects release tags that do not match `v` plus that value. The OCI revision label remains the source commit SHA. `CHANGELOG.md` keeps pending changes under Unreleased until an explicitly requested release.

## Presentation and deployment

`GET /api/events` is a public, read-only SSE stream under the same viewing policy as workspace reads. `revision` events carry `{revision}`; `unavailable` events indicate an observation failure without exposing diagnostics. One observer reads committed SQLite revisions every 0.5 seconds, including writes from UI, MCP and external explicit imports. Each subscriber has a one-item latest-notification queue, at most 128 streams are accepted, and comment heartbeats are sent every 15 seconds. Reconnects receive the latest observation, not an event history. The stream sets `X-Accel-Buffering: no` and no-store headers; ingress must allow unbuffered long-lived responses. Disconnects release subscriptions. Application shutdown bounds graceful HTTP draining.

Browsers fetch canonical state after a newer revision, ignoring duplicates and snapshots older than a newer local save. Editor-open, drag and pending-save locks defer refreshes; editor revisions remain attached to their drafts. Closing/finishing resumes refresh. Existing stale-save conflict handling remains unchanged. View selection, filters, calendar placement and collapse state are preserved where valid. Offline/error states are visible; browser reconnection and failed-snapshot retry recover missed changes. No credentials travel through the event stream.

What if is a local, read-only assumption for one active blocker's actual scope. The panel contains only a blocker selector and Assumed blocker end, with a calendar and adjacent ±1 day controls. End defaults to today and must be today through 365 calendar days ahead, inclusive; blocking includes the selected day, with resumption on the following eligible day. Discovery/start of blocking, scope and every other blocker stay unchanged. The same single timeline shows the resulting forecast; there are no parallel comparison lanes or duplicate task frames. Completed tasks and unrelated work remain fixed. Not-started affected work moves after resolution, with Activity/Stream dependencies cascading and weekend settings respected. In-progress work retains its known actual start or estimate anchor and past planned work; future effort is approximated as ceil(full estimate × (100 − progress) / 100) scheduled days. Saved Started at 0% also counts as in progress. Percentage-to-effort is approximate, not execution evidence. One continuous frame contains solid grey non-working weekends and red blocker/waiting sections, without letters or hatching; names stay anchored to the frame's start. Controls update immediately without a Preview button; Return to plan clears the assumption. Drag is disabled while a valid assumption is displayed; nothing is saved. New revisions recalculate against canonical state while preserving the selected blocker/date; a closed/removed blocker requires an explicit new selection rather than silently choosing another. Summary delay and deadline margin/overrun use calendar days. PocketHive runs/journal integration stays deferred.

The same process serves the existing HTTP API, website, and `/mcp` Streamable HTTP endpoint. Pinned dependencies are in `requirements.txt`; the official MCP SDK owns discovery, protocol negotiation, tool input/output schemas, and transport framing. The host application's lifespan starts the SDK session manager. Stateless mode avoids retaining a client identity or session between requests.

MCP reads follow the public view-only policy. Every mutating call resolves the bearer header through the same `require_editor` owner as HTTP writes. No token is accepted as a tool argument or persisted. Scoped commands require an integer `expected_revision`, read a plan by stable ID, compose only the specified edit, and save through `planner_store.write`; its transaction rejects a racing HTTP or MCP writer. Patchable fields belong to the command contract, while persisted-data validation stays in the store. IDs, collections, and `resolvedAt` cannot be patched. Create rejects existing IDs instead of silently upserting. No MCP deletion or bulk replacement tool is exposed.

MCP uses a one-megabyte request limit. Host/Origin checks remain enabled with localhost defaults; remote addresses and browser origins require explicit `POCKETPLANNER_MCP_ALLOWED_HOSTS` and `POCKETPLANNER_MCP_ALLOWED_ORIGINS`. This is a trusted-environment bearer integration, not a new OAuth issuer or an unattended service-account system. TLS and a future Rovo credential/approval contract must be provided explicitly, not inferred.

The viewport contains bounded Plan, Issues, Streams, Types, Data, and Plans panels. Calendar windows are 7/14/21/28 days with explicit navigation. Plan selection and calendar placement communicate timing. There is no resource scheduling engine.

Timeline stream headers toggle their activity groups using keyboard-accessible buttons with expanded state and controlled group IDs. Overall progress remains visible when collapsed and includes every activity in the stream, independent of the calendar window. Activity bars use one continuous calendar frame; excluded weekends are grey and blocker/waiting periods red. Enabled working weekends keep the Activity's color. Activity and Stream names stay at the frame's start, not a future work segment. Progress fills scheduled work, not those gaps. Collapsed streams retain one frame with the stream name, grey excluded weekends and marked pauses. Their work/progress projection uses the union of scheduled days and preserves explicit weekend work. Summary fill uses aggregate progress across that union, not an execution-history claim. Empty streams have no summary bar or numeric percentage. Dragging an independent activity frame moves the whole activity, keeps the full duration and weekend option, recalculates dependent schedules. Auto-scheduled activities instead have read-only projected starts and cannot drag independently; clear the dependency or move the predecessor. Dependency arrows and tooltips identify auto-scheduled activities/streams. Weekday-only drops on Saturday/Sunday snap forward to Monday; opted-in activities can start on weekends. Collapse state is presentation-only, scoped to each plan for the current page visit; viewers can toggle it without auth or workspace writes.

Activity details show Started, a synchronized 0–100 slider, native numeric stepper and Done in one row. The numeric field is the submitted progress owner; invalid drafts stay visible for form validation. Started stages an explicit start action; Done stages 100% and completion. Save persists, Cancel discards. A saved start is immutable and its button disabled. Viewers cannot change these controls. Full estimate/planned finish, projected finish/approximate remaining work, actual elapsed calendar days and recorded blocking are separate values. Projection includes normal known blocking; What if changes the selected blocker's expected end. Recorded completion frames cannot be dragged to alter factual timing.

Timeline activity names indent by their activity-dependency depth within the stream; siblings share a level and chained successors indent further. Indentation is bounded to keep narrow labels readable and affects neither row order nor dates, bars, percentage alignment or saved state. Stream-level dependencies alone do not indent activity names.

Activity status/description is limited to 1,000 characters in the store and uses maxlength=1000 in the editor. Stream and issue descriptions keep their 2,000-character limits; plan descriptions keep 12,000. Browser maxlength counts UTF-16 code units, so non-BMP text can reach the browser limit sooner than the server's Python character count; browser input never exceeds the server limit.

Issue lifecycle actions explicitly close or reopen an issue and submit the validated current form through the existing mutation contract. Save and the normal Enter shortcut retain the current lifecycle state; Cancel discards unsaved edits. An explicit lifecycle action supplies its target through the hidden open-state field during form submission; the canonical persisted status remains the boolean `open`. The lifecycle button is not the default submit action, so Enter cannot inadvertently close or reopen an issue. Viewers cannot submit lifecycle actions. The Issues list defaults to Active and can show History; the blocker classification filter works within either status view. The full-block warning's blockers action always selects Active. `descriptionIncomplete` is informational only: its checkbox sits beside Description and adds an `incomplete` list label, without changing dates, progress, or blocker scope/effect.

List blocker classification and affected-stream scope are noninteractive labels. Only the issue title opens its details; blocker and scope changes are made inside that editor. Closed issues show their resolution date/time in the list and details, formatted in the browser's local timezone with the saved timestamp available in the tooltip. Older closed records without timestamps show Not recorded.

Blocked unfinished activity rows pulse red; stream headers pulse when at least one unfinished activity is blocked. Only when every unfinished activity of the active plan is blocked does entry display the animated `BLOCKED!` dialog. Acknowledgement is local to the current page/plan visit and does not resolve issues. The blockers action dismisses the dialog and filters Issues to open blockers. Reduced-motion mode uses a static warning and tint.

The PocketHive Press Set uses ink `#080b16`, panel `#111626`, paper `#f7f8ff`, honey `#ffc107`, cyan `#36dfff`, violet `#b49aff`, muted `#a8b2c8`, and Arial typography. Authored type colors remain editable data.

The PocketPlanner wordmark uses the same typography declaration as the PocketHive and HiveForge source logos: Inter, Segoe UI, Arial, sans-serif; weight 800 at 76px for the name and weight 500 at 26px for the subtitle. The approved `simple test plan` subtitle spans the full name width. `web/pocketplanner-topbar.svg` is the compact header asset without a subtitle; `web/pocketplanner-logo.svg` retains the full large-logo variant for README/documentation; `web/pocketplanner-mark.svg` is the favicon.

SQLite has one workspace writer and survives container updates through mounted storage. Deploy one replica. HiveForge renders a Swarm stack and owns its execution; durable state lives outside replace-managed artifacts. Plans keep stable IDs to support a future, separately contracted PocketHive execution integration.

The deferred [PocketHive integration design](POCKETHIVE_INTEGRATION.md) extends local actual Activity timestamps with many-to-many run associations, optional journal evidence and requirement-document references. No PocketHive execution integration is implemented.

Image builds apply available Debian package updates, use pinned pip only during dependency installation, and remove pip from the runtime image. Application dependencies remain pinned in `requirements.txt`. Rebuild with a refreshed base and rescan the resulting image; unavailable upstream fixes must not be represented as resolved merely because the app does not exercise the affected utility.
